# API Surface

> **2026-05 â€” Postgres migration in progress.** DB engine is Postgres 16 (docker compose service `atlas-open-postgres`). Migration history collapsed to a single Knex baseline: `packages/api/src/db/migrations/001_baseline.ts`. Query layer: **Kysely** for queries (type-safe, async) and **Knex** for schema migrations. Side tables (`comments`, `issue_events`, `agent_runs`, `notifications`) now reference `items(id)` directly via a single `item_id` FK with `ON DELETE CASCADE`. Issue links now live in `item_links(from_id, to_id, relation_type)` where `relation_type âˆˆ {relates_to, depends_on}`. Since migration 037 (ADR 0015) `items.type` is `task` or `sub_task` (text + CHECK); the per-kind routes (`/api/tasks/...`, `/api/sub-tasks/...`) project rows through `services/items.ts` (`rowToTask` / `rowToSubTask`).

Fastify server in `packages/api/src/server.ts`. All routes registered as plugins from `packages/api/src/routes/`. All requests validated against Zod schemas in `@atlas/shared/schemas`. Responses use snake_case fields matching `@atlas/shared/types`.

Base URL in dev: `http://localhost:4301`. In prod (`pnpm prod`, `ATLAS_ENV=prod`): `http://localhost:5301`. Web calls go through `packages/web/src/api/api.ts` and are proxied via vite's `/api` â†’ `API_PROXY_TARGET` rule, so the bundle itself never sees an absolute URL.

Live Swagger UI at `/api/docs`; OpenAPI 3 JSON at `/api/docs/json`. This markdown file is the human index; the JSON is what's actually served. Routes without `schema:` blocks appear in the spec with method + path only (no body/response details) â€” fill in `schema:` on a route to get richer docs.

## Routes

### `routes/agents.ts` â€” Agents
**Why this group exists**: Agents are the configurable AI workers that act on behalf of the Owner. CRUD is exposed here because only the Owner configures, pauses, and routes them; the MCP layer intentionally does not touch this surface (external AI clients should never create or rename agents â€” that's an Owner-only concern). Checklists and memory live under the agent rather than separate top-level resources so authorization is always anchored to one agent. Git delivery is not an agent concern: the Task runner commits, pushes and opens the PR — see `routes/workflows.ts`.

### `routes/roles.ts` â€” Roles (A08)
**Why this group exists**: `roles` is the lookup table behind `agents.role_id`. Its slugs are fixed by `SdlcRole` in `@atlas/shared` (the runtime never invents roles), so the only runtime edit is the Owner changing a role's label, description or default prompt. The runner never reads `roles.default_prompt_md` at dispatch. Agents installed from this edition's catalog have `role_id = null`.

### `routes/projects.ts` â€” Projects
**Why this group exists**: Projects are the only top-level work container â€” every issue, schedule, and per-project guardrail tunnels through a project_id. Clone, reclone, and delete are exposed as POST/DELETE that spawn subprocesses (`clone-runner`, `reclone-runner`, `delete-runner`) and stream SSE because they're long-running and can fail mid-way; doing them inline would block the request handler and lose user feedback. The per-project `/env` endpoints are intentionally separate from the workspace-wide `/settings/env` so secrets stay scoped to one repo.

### `routes/tasks.ts` — Tasks (ADR 0015)
**Why this group exists**: A **Task** is the top-level item (migration 037 turned every epic into one) and the only item that runs: its assigned agent works it in one run that delivers one branch and one PR (one per repo for a multi-repo Task). **2026-10-16 — delivery hardening (migration 013).**
- **Toggle re-checked at the flush.** A hold stores its event key (`external_event_key`); when the window ends a row whose toggle is off by then becomes `external_status='none'` + `failure_reason='Skipped: event turned off while held'` and is not sent. The log shows it as **Skipped** with **Send now**. Reminders and auto-fetch have no key, so toggles never skip them.
- **Stuck sends recovered.** Every in-flight send stamps `external_claimed_at` (`updateExternalStatus(…,'pending')`, and the flush's `claimDeferred` CAS). Settling (`sent`/`none`/`failed`) clears it. The same minute flush (`flushDeferredExternal`, outside quiet hours) calls `reclaimStuck`: a `pending`, unheld row claimed more than 10 minutes ago (`STUCK_SEND_MS`) is re-claimed once (`external_reclaimed=true`, CAS on the old claim) and resent without the held prefix; stuck again, it becomes `failed` with "Send interrupted twice … Press Retry". Partial index `notifications_external_claimed_idx`. Ceiling: a single flush batch that takes longer than 10 minutes to send could see its own tail re-claimed by the next tick.
- **Log-only rows (`in_app=false`).** External-only reminders and MCP sends keep their row (Notification Log, reminder fire log) but are left out of the feed, `countUnread` (`/api/counts`, sidenav badge) and Mark All Read; `create()` skips `counts_changed` and web push for them (it still broadcasts `notification_created` so the log refreshes).
- `sendExternalNotification` (the row-less helper) is gone; `sendOwnerExternalMessage(message, eventKey?)` replaces it.

**2026-09-14 — delivery status honesty.** `sendExternalNotification` returns `true` only when a transport actually sent; quiet hours, an off event toggle, or an unconfigured transport return `false`. `sendExternalForNotification` then writes `external_status='sent'` only on `true`, otherwise reverts the row to `'none'` (the schema's existing "no external delivery" value, same as cancel — no new status added), so the Notification Log never shows "Sent" with no channel connected.

**2026-10-16 — quiet hours defer, outward failures, one click target.**
- `sendExternalForNotification(id, message, eventKey?, now?)`: an off event toggle leaves the row `none`; inside quiet hours (and with a channel configured) the row is **held** — `external_status='pending'` + `external_deferred_at=now` (migration 010) — instead of dropped; otherwise it is delivered now. `flushDeferredExternal(now)` runs on the minute tick (`agent-schedule-registry.ts`, right after reminders): once the window is closed it claims every held row with one CAS `UPDATE … WHERE external_deferred_at IS NOT NULL AND external_status='pending' RETURNING`, sends oldest first with the prefix `Held during quiet hours · HH:MM` (the row's created time in the quiet-hours zone), and marks each `sent`/`none`/`failed`. Web push is unaffected (always immediate).
- `isInQuietHours`: `from == to` is an empty window (off). A stored zone the formatter rejects falls back to server-local time instead of throwing; `UpdateNotificationsSchema` now rejects unknown zones (checked with `Intl.DateTimeFormat`, not `Intl.supportedValuesOf`, which omits `UTC` and `Asia/Kolkata` on Node 24).
- New event keys, default ON: `jira.sync_failed` (a new Jira sync failure, `recordSync`) and `workflow.failed` (a Task run parked because something broke — worktree, setup script, step error, delivery, lost step — via `parkFailed`, and a Task that could not start, `reportDispatchFailure`). Questions and reviews keep `item.status_changed:waiting_for_info` / `agent.run_finished_no_item`.
- Reminders and auto-fetch now send through the row they created (tracked in the log, held by quiet hours). A reminder fire creates exactly one row and one `notification_created` (the duplicate SSE is gone); the row carries `reminder_id` (migration 011). `fireDueReminders` skips paused rows, and its CAS claim also requires `status='active'` so a pause that lands mid-tick wins.
- `notificationsService.create` stamps `link_url` at create time with `notificationLinkUrl` (@atlas/shared): explicit link → `/tasks/:id` · `/sub-tasks/:id` → `/reminders` → `/settings?tab=jira` → `/projects/:id`. Producers pass the links that can't be derived: Task runs and dispatch failures `/tasks/:id`, standalone agent runs `/agents/:id/runs/:runId`, terminal `/terminal/:id`. Web push's click URL and the In-App Feed use the same helper, falling back to `/notifications`.

**2026-09-14 — stale `needs_you`.** The list endpoint and the unread count (`notificationsService.list` / `countUnread`) hide `kind='needs_you'` + `event_type='agent_completed'` rows whose linked item is no longer `waiting_for_info` / `in_review`. Rows with no item, and other `needs_you` sources (`agent_error`, terminal idle, auto-fetch), are never hidden — they aren't derived from item status.

### `services/agent-schedule-registry.ts` — one-minute poller

A single `setInterval` ticks every 60s, first tick aligned to the next wall-clock minute (`startAgentSchedulerPoller`, started from `main.ts`). Agents have no schedule or queue of their own; the tick (`tickAgentScheduler`) runs, in order, each step isolated in its own try/catch:

1. **Stuck-run watchdog** (`sweepStuckRuns`) — `in_progress` runs started > 30 min ago with no `output_text` → `error`, then `onStepFinished` so the Task run retries or parks.
2. **Reminders** — `remindersService.fireDueReminders`.
3. **Quiet-hours flush** — `flushDeferredExternal` sends held notifications once the window closes.
4. **GitHub App tokens** — pre-warm installation tokens within 15 min of expiry.
5. **Run reconcile** (`reconcileWorkflowRuns`) — parks any `running` Task run with no live step and `updated_at` older than 10 min (`WORKFLOW_RECONCILE_AFTER_MS`; longer than a worst-case End push + PR).
6. **PR state** (`externalLinks.syncReviewedTaskPrs`) — re-reads the PRs of Tasks in review.
7. **Jira bridge** (`jiraSync.tick`, ADR 0016) — only when `jira_config.enabled`. When `poll_interval_minutes` have passed since `last_sync_at`: a full sync (pull + push with digests). Otherwise a push only: it posts a Jira comment for each linked Task whose status changed since the last post. It runs before dispatch so a Task it just queued starts this tick.
8. **Task dispatch** (`tickWorkflowDispatch`) — starts the oldest `ready` Tasks that have an assigned agent, no live run, no open `depends_on` target and no repo shared with another live run, up to `MAX_PARALLEL_RUNS` (3) running at once. Parked runs hold no slot.

Queuing a Task, `finishRun` and `cancelWorkflowRun` also kick one dispatch pass immediately (`kickWorkflowDispatch`), so a queued Task never waits for the 60s tick.

### `routes/cli-sessions.ts` — Terminal (PTY-backed CLI sessions)
**Why this group exists**: The Terminal pages run real `claude` / `copilot` CLIs in server-side ConPTY sessions (`cli = ollama` runs `claude` with the Ollama env overlay); the browser is only a viewport. REST manages the session lifecycle; one WebSocket per attached pane carries the byte stream.

**Two kinds of session share this table and every endpoint below.** A **project** session is scoped to an Atlas-provisioned worktree. **WS stream contract** (`services/cli-session-host.ts`): terminal geometry is **pinned** — PTY, server mirror, and every browser pane all run at the shared `TERMINAL_COLS × TERMINAL_ROWS` (120×30, `@atlas/shared`) for the whole session lifetime, and `pty.resize()` has zero call sites. This is the fix for the ConPTY "zombie characters": ConPTY answers any resize by repainting its whole buffer with reflow semantics that never exactly match xterm's, so any moment where the PTY's believed width and a viewer's width differ strands unerased cells — and with one PTY and N viewers, dynamic geometry can never be mismatch-free. Browser panes adapt by scaling their font, never the grid. On attach the server first sends a **`{cmd:'ptyInfo'}` text frame** — on a Windows host it carries `windowsPty: {backend:'conpty'|'winpty', buildNumber}` (node-pty's own gate: conpty iff build ≥ 18309), which the browser applies to xterm's `windowsPty` option (also passed to the headless mirror at creation) to honor ConPTY's other repaint assumptions. Then the server replays a **serialized screen snapshot** — a clean, well-formed VT stream produced by a per-session `@xterm/headless` mirror (`services/terminal-screen-state.ts`) — then forwards raw PTY bytes live, each byte delivered exactly once (snapshot XOR live). The snapshot contains no DSR queries and is always laid out at the pinned grid, so reconnect/refresh never renders mid-sequence "zombie" characters. Inbound: raw bytes are typed into the PTY; the JSON control envelope `{cmd:'resize'}` is recognized, consumed, and **dropped** (kept only so a stale client's frame can never be typed into the shell as literal JSON). Auth: WS upgrades bypass the POST-only write gate, so the route accepts only trusted browser Origins or `?token=<ATLAS_MCP_TOKEN>`.

## MCP tool catalogue (Theme 07)

The MCP server (`packages/mcp/src/server.ts`) registers tools via
`registerAllTools()` in `packages/mcp/src/tools/index.ts`. Each tool is a
thin wrapper over an `api-client.ts` method which in turn hits a REST
route. The token gate on the API rejects writes from non-trusted origins
unless `X-Atlas-Token` matches `ATLAS_MCP_TOKEN`.

**A06** â€” every tool's registration metadata (`name`, `title`, `description`,
`group_name`, `sort_order`, `excludeFromCatalog?`, `inputSchema`, `handler`)
lives in a typed `<GROUP>_TOOLS` array in `packages/mcp/src/tools/<group>.ts`.

`tool-catalog-sync` projects from it so the Allowed Tools picker matches the
MCP surface automatically. Performer-persona prompts include a Working
Protocol bullet directing agents to optionally call `agent_memory` (`op: 'update'`, `mode: 'append'`)
for generic behavioral lessons; reviewer prompts carry a symmetric clause.
Both invoke the same memory boundary rule embedded in the tool description.

**B05** â€” `update_item action='add_link'` is intentionally
**agent-discretionary**: no Working Protocol bullet mentions it in any
performer or reviewer prompt. The MCP tool description is the only trigger â€”
agents may call it when they discover a missing dependency, and the UI's
`<RelatedItemsCard>` is the Owner-side counterpart (both hit
`POST /api/issues/:type/:id/links`). The runner does not parse agent output
to infer links, and nothing auto-links at step or End time. The read-side is
non-discretionary: every prompt includes a `## Related items` section
listing existing links up-front (the `related_links` field on the `get_item`
envelope), so a fresh `get_item` mid-run is rarely needed. Full mechanism in
`.agents/data-model.md` Depends-on section.

`packages/api/src/db/migrations/` - knex-driven PG migrations. **As of 2026-10-23 Atlas Open's history is one baseline of its own schema** (ADR 0032): the 20 files it shipped in 1.0.0 (the commercial edition's 001-019 plus `020_solo_runs.ts`) were squashed, and the schema only the commercial edition uses was dropped: the `team_config` and `published_workflows` tables and `workflows.{push_to_default, max_loops, max_parallel_runs, schedule_weekday, marketplace_pulled_at}`, `projects.default_workflow_id`, `item_external_links.ci_fix_attempts`, `run_gate_results.log_path`. **Regenerating the baseline.** Not needed when a new numbered migration lands - knex tracks each independently in `_knex_migrations`. Only on a deliberate re-squash. Apply every migration to a clean DB, then:

1. `pg_dump --schema-only --no-owner --no-acl --exclude-table='_knex_migrations*'`
2. `pg_dump --data-only --column-inserts --no-owner --no-acl -t cli_models -t roles -t guardrail_rules -t settings -t workflows`, appended before the trailing "dump complete" comment.

Then strip from the **combined** result - both passes emit these, and `psql` hides both failures:

- Every `\restrict` / `\unrestrict` line. psql treats them as meta-commands and swallows them; knex sends the file as SQL and dies with `syntax error at or near "\"`.
- Every column-0 `SET ...` and `SELECT pg_catalog.set_config(...)` line. `set_config('search_path', '', false)` is the dangerous one - it blanks the search path for the rest of the session, and knex's own follow-up `insert into "_knex_migrations"` then fails with `relation "_knex_migrations" does not exist`. Every object in the dump is schema-qualified, so dropping the preamble is safe.

Pass 2 is not optional: `--schema-only` emits no rows, and a baseline without them installs with no CLI models, no guard-rails and no settings singleton to onboard into. The `cli_models` count grew 16 -> 19 -> 23 across the squashes, so an old INSERT block must never be carried forward unread.

**Verify by running the new baseline through `run-migrations.ts latest` against a second clean DB and diffing both `pg_dump` outputs - never by `psql -f`**, which swallows exactly the artifacts that break knex. Both failure modes above were hit during the 2026-09-20 re-squash; the 2026-09-28 one followed this recipe and diffed identical.

**Migration tests.** A spec that imports `up`/`down` from a migration module dies with the squash - it tests a transition that no longer exists as a discrete step, because the baseline is that transition's end state. Six were deleted on 2026-09-20 (034, 037, 039, 041, 044, 045); `backfill-skipped-verdicts.test.ts` (015) on 2026-09-28; `park-kind-backfill.test.ts` (014) on 2026-10-23. A spec that asserts the **live schema** survives: `workflows-migration.test.ts` (035) and `hot-path-indexes.test.ts` (021) both did. Write the latter kind.

**Append-only rule.** Schema changes after 2026-10-23 go in new numbered files (`002_*.ts`), never as edits to `001_baseline.ts` or `001_baseline.sql`. `migrations-rollback.test.ts` asserts every migration exports `down()` and that numbering is contiguous from 1.

**Existing-DB cleanup.** Any DB that applied the pre-squash migrations carries rows in `_knex_migrations` for files that no longer exist. `run-migrations.ts` checks for that before knex runs and exits with a "reset it" message naming the files (knex alone would die with "migration directory is corrupt"). Two ways to recover:

- **Reset** (recommended): `pnpm db:down:purge && pnpm dev`. Since 2026-10-23 that only touches the `atlas-open-pg` volume.
- **In-place rewrite** (keeps data, only from a DB that was fully at `020_solo_runs.ts`): `DELETE FROM _knex_migrations WHERE name <> '001_baseline.ts';` then re-run `pnpm -F @atlas/api db:migrate` (now a no-op). The dropped tables and columns stay behind, unused.

`atlas_open_e2e` self-heals - `e2e/global-setup.ts` drops and recreates it every run. `atlas_open_test` does not; drop it manually after a squash.

Seed data: `packages/api/src/db/seed.ts::runSeed` syncs the on-disk marketplace catalog (`packages/api/src/marketplace/catalog/<id>/{manifest.json,prompt.md,memory.md,checklists.json,tests.json}`, 7 entries: `agent-solo` plus `agent-ai-news`, `agent-ai-readiness`, `agent-jira-to-epic`, `agent-knowledge-base`, `agent-market-research`, `agent-regulations`) into `marketplace_agents` + `marketplace_agent_checklists` (each entry's `version` is taken verbatim from its `manifest.json`, **not** derived from `content_hash` — the hash is stored but no longer drives bumps; the whole catalog was reset to `version: 1` on 2026-09-22 and again on 2026-09-28 (ADR 0025) so a release starts at v1), then upserts `guardrail_scripts` (`prereqs` only). It seeds no `agent_templates` rows: no shipped agent reads `.atlas/templates/` (the templates-assembler still writes whatever rows exist, so the folder is empty by default). It **never writes `agents`** — agents exist only once the Owner installs a catalog entry. `catalog-loader.ts` strips retired agent routing/scheduling keys from any older `manifest.json`. The 4 reference tables (`cli_models`, `roles`, `guardrail_rules`, `settings`) are seeded by `001_baseline.sql`. Idempotent.

Dev-only reset: `pnpm -F @atlas/api db:reset` drops + recreates the `atlas` database in the local Postgres container and re-runs migrations. Pair with `pnpm -F @atlas/api db:seed` to repopulate the marketplace catalog.

## Response compression (ADR 0031)

Every JSON/text response over 1 KB is compressed when the client sends `Accept-Encoding`: Brotli (quality 4) preferred, gzip otherwise (`plugins/compression.ts`, an `onSend` hook). Streams (file downloads) and the hijacked SSE route (`/api/events`) are not compressed.
